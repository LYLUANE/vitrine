Painel Arquitetura e código
Como funciona por dentro

Seis módulos, uma regra: nenhum pedido perdido, nenhum duplicado

O conector roda de dois jeitos: por agendamento, buscando o que mudou desde a última rodada, e por webhook, quando o marketplace avisa que entrou pedido. Os dois caminhos passam pelo mesmo funil de retry, normalização e gravação idempotente.

Fluxo dos dados

Do pedido feito no marketplace até a planilha do financeiro
consulta agendada (pull)notificação do marketplace (push)

Cursor só avança no sucesso

Se um pedido falhar de vez, o cursor fica onde estava e a próxima rodada busca de novo. Pedido pulado em silêncio não acontece.

Webhook não é confiável sozinho

Plataformas reenviam eventos e às vezes deixam de enviar. Por isso o webhook acelera, e o agendamento garante.

Dinheiro em centavos

Toda conta de valor é feita em inteiros. O total do ERP é conferido com o que o marketplace diz ter cobrado.

O código, de verdade

Trechos lidos dos mesmos arquivos que rodam no painel. Nada foi reescrito para a vitrine.

Na versão para o cliente

  • A API oficial da plataforma que ele usa (Mercado Livre, Shopee, Bling, Tiny ou outra), com o OAuth dela.
  • Servidor Node com o mesmo conector: fetch no lugar do mock.
  • Agendamento por cron e endpoint HTTPS para os webhooks.
  • Banco de dados no lugar do repositório em memória, ou envio direto para o ERP do cliente.

O que vai junto

  • Alerta por e-mail ou WhatsApp quando uma rodada falha de vez.
  • Planilha ou painel com os pedidos do dia, filtros e exportação.
  • Tokens guardados em variável de ambiente, nunca no código.
  • Documento curto explicando como rodar, onde ver os logs e como reprocessar.
